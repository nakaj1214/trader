# scope-router — 詳細手順

チャットからの実装依頼を受けたとき、作業規模を判定して適切なワークフローへルーティングする。

---

## ステップ1: 依頼の分類

まず依頼が「実装・修正の依頼」かを確認する。以下は **対象外**（ルーティングしない）:
- 質問・調査・説明依頼（「〜を調べて」「〜を教えて」）
- `/create-plan`、`/propose-one` などスキルを明示的に指定された場合
- すでに proposal.md や plan.md が存在し、実装フェーズに入っている場合

---

## ステップ2: 規模の判定

依頼内容を読んで、**変更が必要なファイル数と複雑さ**を推定する。

### 判定基準

| 規模 | 条件 |
|------|------|
| **小・単純** | 1ファイルのみ変更、ロジックが単純（値変更・表示修正・軽微なバリデーション追加など） |
| **小・複雑** | 1ファイルのみだが、ロジックの再設計や複数の処理フロー変更を伴う |
| **中・大** | 複数ファイルにまたがる変更（Controller + View + JS、Migration + Model + Controller など） |

### 複雑と判断するシグナル

- 新しいDB列・テーブルが必要
- 既存の処理フローを根本から変える
- 複数のレイヤー（Model / Controller / View / JS）をまたぐ
- 「どう実装するか」が自明でない（設計の判断が必要）

---

## ステップ3: ルーティング

判定結果に応じて以下のアクションを取る。

### 小・単純 → そのまま実装

ユーザーへの通知は不要。通常通り実装を進める。

### 小・複雑 → create-plan に派生

ユーザーに一言伝えてから `create-plan` スキルを呼び出す:

```
この変更は1ファイルですが複雑なため、実装計画を作成します。
/create-plan
```

### 中・大 → create-proposal → create-plan に派生

ユーザーに一言伝えてから `create-proposal` スキルを呼び出す:

```
複数ファイルにまたがる変更のため、まず要件書を作成します。
/create-proposal
```

`create-proposal` 完了後、`create-plan` が自動的に続く（create-proposal の仕様による）。

---

## 判定に迷ったとき

「1ファイルか複数か」が判断しにくい場合は、**複数寄りに判定**する（過剰計画より計画不足の方が問題が大きい）。

「小・単純か小・複雑か」が判断しにくい場合も、**複雑寄りに判定**する。

---

## 注意事項

- バグ修正の場合、CLAUDE.md のルールにより `verify-before-fix` が先行する。本スキルはその後の「実装フェーズの規模判定」として機能する
- ユーザーが「小さな変更だから直接やって」と言えば、ルーティングをスキップして実装する
