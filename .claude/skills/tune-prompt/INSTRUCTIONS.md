# tune-prompt: 詳細ワークフロー

## Phase 1: 静的検証

対象のスキル/コマンドファイルを読み、以下を確認する:
- description と本文の内容が一致しているか
- 曖昧な指示・省かれた前提がないか
- トリガー条件が明確か

問題が見つかった場合はその場でメモし、Phase 5 の修正候補とする。

## Phase 2: ベースライン準備

このプロジェクトで現実的なシナリオを 2〜3 個作成する。
各シナリオに「期待する動作のチェックリスト」を添える。

```
シナリオ例:
- prompt: "ユーザーが実際に送りそうな自然な指示"
- expected: チェックリスト形式の期待動作
- assertions: 確認すべき具体的な動作（3〜5項目）
```

## Phase 3: バイアスのない実行

Agent ツールで **新規サブエージェント** を起動し、対象スキルを実行させる。

```
制約:
- 同一セッションのエージェントは使わない
- 「うまくやって」ではなく、実際のユーザーが送るような指示を与える
- 実行過程と判断根拠を記録させる
- 「ここが曖昧だったので推測した」「この指示がなかった」を報告させる
```

## Phase 4: 二層評価

| 評価軸 | 確認内容 | 重み |
|--------|---------|------|
| 成功/失敗 | 期待通りに動いたか | - |
| 精度 | チェックリストの要件充足率 % | 中 |
| ステップ数 | 無駄なステップはあったか | 低 |
| 定性レポート | 曖昧だった点・裁量で判断した点 | **高** |

**定性レポートを最重視**。「ここが曖昧だったので推測した」が改善の最大の手がかり。

## Phase 5: 最小限の修正

- 1 イテレーションで修正するテーマは **1つだけ**
- 複数問題を一度に直さない
- 修正箇所と理由をコメントで残す

## Phase 6: 再評価

- **前回と異なる** 新規サブエージェントで再実行
- 同じエージェントを使い回さない

## Phase 7: 収束判定

連続 2 回の評価で改善が見られなければ完了とする。

---

## 出力形式

```markdown
## プロンプト調整レポート: [対象スキル名]

### 実行シナリオ
- シナリオ1: ...

### 評価結果（イテレーション N）
- 成功/失敗:
- 精度: X%
- 定性レポートの要点:
  - 曖昧だった点: ...
  - 裁量で判断した点: ...

### 修正内容
- 変更箇所: [ファイル:行]
- 修正テーマ: ...

### 収束判定: [継続 / 完了]
```

## 停止条件

以下のいずれかで停止しユーザーに報告する:
- 収束判定「完了」に達した
- 5 イテレーション経過しても改善しない（根本的な設計見直しが必要）
