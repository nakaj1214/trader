# 価格取得の新旧経路の同等性確認（REQ-042 Step 7）

確認日: 2026-10-01（水、取引時間中）
対象: 旧経路（銘柄ごとの `yf.Ticker().history()`）と、新経路（`src/data/forward_prices.py` の一括 `yf.download(auto_adjust=False, actions=True)` → 2つの基準を導出）
環境: yfinance 1.7.0。実データの API 呼び出しのみで、リポジトリやキャッシュには書き込んでいない。

## 結論

**新旧の経路は、値が同一である。** 観測された差はすべて、Yahoo 側が「取引中の当日を含む期間」のリクエストで値を揺らしていることによるもので、旧経路どうしでも同じように発生する。経路の切り替えが原因の差は見つからなかった。週次 CI（日曜 09:30 JST）は取引時間外に実行され、価格ハッシュを保存するのも schedule 実行だけなので、この揺れの影響を受けない。

## 確認した内容

### 1. 新旧の比較（分割・配当・ETF）

| 銘柄 | 内容 | 期間 | 分割のみ基準 | 配当込み基準 |
|---|---|---|---|---|
| 7203.T | 1:5 分割（2021-09-29） | 2021-08〜2021-12 | 一致（差 0、ハッシュ不一致 0/82） | 一致（差 0、0/82） |
| 8058.T | 1:3 分割（2023-12-28） | 2023-11〜2024-02 | 一致（差 0、0/60） | 一致（差 0、0/60） |
| 1306.T / 9984.T / 6758.T | 配当、ETF（ベンチマーク） | 2025-06〜**当日を含む** | 一致（1回だけ 9984.T の1行で1円差） | 一部の実行で、16〜131行に最大 5e-4 円の差 |

過去の期間（分割の2銘柄）は、日付・値・価格ハッシュがすべて完全に一致した。

### 2. 差の原因の切り分け

| 試験 | 結果 |
|---|---|
| 新旧の比較を、**当日を除く**期間（〜2026-09-30）で8回繰り返す | 8/8 回とも完全に一致 |
| **旧経路どうし**を、当日を含む期間で12回繰り返す（間に別のリクエストを挟む） | **10/12 回でハッシュが変化**（最大の相対差 2.65e-4） |
| 旧経路どうしを、当日を除く期間で12回繰り返す | 0/12 回（完全に一致） |
| 一括取得した生データと `history()` の生データ（当日を除く） | 全列（OHLC、Adj Close、Volume）で差 0。型も同じ（float64、Volume は int64） |
| yfinance の `auto_adjust()` を `history()` の生データに適用 | `history(auto_adjust=True)` と完全に一致（新経路の導出方法が正しいことの確認） |

- 配当込み基準の小さな差（相対で約 6e-8、5e-4 円/3800 円）は、float32 の精度程度である。Yahoo は値を float32 で返しており、取引中は配当調整後の終値（`Adj Close`）を毎回計算し直しているとみられる。
- 分割のみ基準の1円差は、当日の足（取引中に値が動く）が2回のリクエストの間で変わったものとみられる。

## CI への影響
- 週次の forward validation は日曜 09:30 JST に実行され、当日に取引はないので、揺れの条件に当たらない。
- 価格ハッシュを保存する `persist-price-hashes` job は `schedule` 実行だけで動く。平日に PR や手動実行で検証が走っても、ハッシュは保存されない。

## 別件の気づき（今回のスコープ外）
- 価格ハッシュは値を小数9桁まで丸めて比べるが、Yahoo のデータは float32（有効数字7桁程度）である。そのため、Yahoo が値を計算し直すと、価格の実質的な変化がなくてもハッシュが変わり「改訂」として記録されうる。これは今回の切り替えとは無関係で、旧経路にもある性質である。対策（例: 有効数字6桁で丸める）は、ハッシュの形式が変わり一度だけ全件が改訂扱いになるため、行うなら別要件にする。
