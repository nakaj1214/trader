## 使い方

1. 下の「推奨順」から 1 件選び、`verify-before-fix` に ID を指定して渡す（例: 「ISSUE-15 を verify-before-fix で」）。
2. Phase 1 は各項目の「現象」、Phase 2 は「仮説と検証方法」を出発点にする。記載の再現は過去の結果なので、Phase 3 で再実行して確認する。
3. 1 件の修正・検証が終わってから次へ進む。複数件を同時に直さない。

## 全項目共通の制約

- 外部 API・実 Slack・実 Sheets・永続キャッシュ・保存済み snapshot・archive に触れない。検証は fake / synthetic と一時ディレクトリで行う。
- スコア・閾値・重み・Q06 閾値（ticker 10 / signal date 5 / 最大業種比率 50%）を変更しない。Growth（G01〜G07）に進まない。
- 修正で正常入力の候補・スコア・評価結果が変わる場合は、変化が修正の意図どおりか説明する。
- 既存テストを新実装に合わせて書き換えるだけの修正は禁止。修正前に失敗するテストを先に用意する。
- **今回の教訓**: 前回の修正は、欠損値・値の型・複数日にまたがる境界の検証が不足して回帰を生んだ。各項目で、(a) 欠損・NaN・不正な型、(b) 複数日・複数 run をまたぐ場合、(c) 修正が呼び出される上流・下流の境界、を回帰テストに含めること。
- 改行コード（CRLF/LF）を保つ。Python スクリプトでファイルを書き換える場合は、`newline=''` で読み書きするか、Edit ツールを使う。

## ISSUE-15: 古い保留日の日足安値が欠損すると「接触なし」で通過する（ISSUE-04 の回帰）

- **出典 / 分類 / 重大度:** Codex 独立監査 #3 / B / P1
- **現象:** 1 分足が保持期間（30 日）より古く取れない保留営業日は、日足で判定する（ISSUE-04 の修正）。このとき日足の安値が NaN だと、`NaN <= stop` が False になり、「接触なしを証明できた」として通過する。チェックポイントが現在日まで進み、その区間は二度と見直されない。
- **再現条件（Codex）:** 日足 High / Close = 100、Low = NaN、出来高は正、1 分足なし、30 日超の保留日。`run` は `status=ok`、`triggered=False`、チェックポイントを現在日に進めた。実取得関数（`fetch_split_adjusted_history`）への fake 応答から作った履歴を、そのまま監視に渡して確認。
- **期待:** 安値が不明なら「接触なし」を証明できないので `incomplete` とし、以前のチェックポイントを保つ。
- **根拠箇所:** [_daily_could_touch](../../scripts/run_position_monitor.py#L140)（安値を検証せず比較）、[_recover_daily_only の呼び出し](../../scripts/run_position_monitor.py#L158)、上流 [fetch_split_adjusted_history](../../src/data/live_quote.py#L204)（High / Close は `_positive` で検証するが、Low の欠損は拒否しない）。400 経路の健全性テストは、正常な日足だけを作るため、この境界を検証していなかった。
- **仮説と検証方法:**
  1. 日足判定が OHLC の有限性を検証していない（High）→ Low = NaN・inf・負・0、High < Low、Close が範囲外、のそれぞれを `_recover_pending` に渡し、結果を確認する。
  2. 上流の `fetch_split_adjusted_history` が Low を検証すれば、判定側の防御は不要か（Med）→ 上流で拒否すると履歴全体が失敗する（他の保留日・当日評価に波及する）ため、判定側で `incomplete` にする方が影響が小さいかを比較する。
  3. 確認済みの無取引日（`daily` が全 NaN で出来高 0）の例外が壊れないか（Med）→ 既存の分岐（行 ≈190）が先に `continue` するので影響しない見込み。テストで固定する。
- **修正方針の候補（未確定）:** `_recover_pending` の日足判定分岐の前で、`daily` の Low・High・Close が有限・正で、`Low <= min(Open, Close)`、`High >= max(Open, Close)` を満たすか確認する。満たさなければ `IncompleteQuoteError`（従来の保留と同じ扱い）。確認済みの無取引日は従来どおり通過。
- **受入条件:** 安値欠損・非有限・矛盾（High < Low など）の日足で `status=incomplete` となり、以前のチェックポイントが保たれる。正常な日足と、確認済みの無取引日の挙動は不変。既存の ISSUE-04・C02/C03 の回帰テストが無変更で PASS。
- **baseline への影響:** なし（欠損時の安全側への変更のみ）。

## ISSUE-16: 通知状態の値が配列・オブジェクトだと snapshot 保存より前に例外になる（ISSUE-06 の回帰）

- **出典 / 分類 / 重大度:** Codex 独立監査 #4 / B（潜在欠陥あり）/ P2
- **現象:** `digest_state.json` の値が `[]` や `{}` だと、`state not in {"pending","succeeded"}`（集合への所属判定）が `TypeError: unhashable type` になる。これは監査時点からの欠陥（`_deliver_digest` が例外を投げ、scan が失敗する）。ISSUE-06 で `persist_report` が状態を読むようにしたため、同じ例外が **snapshot 保存より前**に出るようになり、当日の snapshot が作られない。
- **再現条件:** `{"2026-09-07": []}`（または値 `{}`）を保存し、正常なレポートを `persist_report(..., digest_state=...)` に渡すと `TypeError`、当日の snapshot は存在しない。元の状態ファイルは無傷。
- **期待:** 不正な状態は通知だけを止め、snapshot の保存は続ける（ISSUE-06・playbooks の主張どおり）。
- **根拠箇所:** [_digest_states](../../scripts/run_inflection_shadow.py#L231)（行 236 の集合への所属判定）、[_mark_digest_pending](../../scripts/run_inflection_shadow.py#L250)（`except (OSError, ValueError)` が `TypeError` を捕捉しない）、[_deliver_digest](../../scripts/run_inflection_shadow.py#L261)（行 273 も同じ）。既存テストは不正 JSON・未知の文字列・トップレベル配列を扱うが、**値**の配列・オブジェクトは扱わない。
- **仮説と検証方法:**
  1. `_digest_states` の型検査が、値が文字列でないときに `ValueError` にならない（High）→ 値が `[]`・`{}`・数値・`null`・真偽値の各ケースで例外型を確認する。
  2. `_mark_digest_pending` と `_deliver_digest` の捕捉範囲だけ広げる案は、原因（検査の順序）を直さない（Med）→ 検査側を直して `ValueError` に揃える案と比較する。
- **修正方針の候補（未確定）:** `_digest_states` で、値が文字列であることを先に確認してから集合に照らす（不正なら既存の `ValueError` 経路）。
- **受入条件:** 値が配列・オブジェクト・数値・null のとき、`persist_report` は snapshot を保存し、`_deliver_digest` は `failed:digest-state-invalid`、`main` は例外なく終了する。壊れた状態ファイルは書き換えない。既存テストが無変更で PASS。
- **baseline への影響:** なし。

## ISSUE-18: 前日分の pending 通知が、翌市場日の通常実行で再送されない

- **出典 / 分類 / 重大度:** Codex 独立監査 #5 / A / P2
- **現象:** `_deliver_digest` が確認・送信するのは、その実行の `latest_price_date` だけ。9/30 の送信が失敗して `pending` のまま残っても、10/1 の通常実行は 10/1 だけを送信し、状態は `9/30=pending, 10/1=succeeded` になる。過去の pending 日を処理する呼び出しは無い。`playbooks.md` の「pending 日は次の通常実行で再試行」と食い違う（Stage 4B 以来）。
- **再現条件:** 監査時点（`3e9b930`）でも現在でも、同じ結果（再現済み）。
- **期待:** `playbooks.md` の記述と整合させる（過去の pending 日も回収する）、または、記述を実態に合わせる。
- **根拠箇所:** [_deliver_digest](../../scripts/run_inflection_shadow.py#L261)、状態は 30 日分で切り捨てられる（`_write_digest_state`）。現在の明示再送（`resend_digest`）も最新日だけを使うので、前日の回収にならない。
- **仮説と検証方法:**
  1. 過去の pending 日を処理する経路が無い（High）→ 再現を `_deliver_digest` と `main` の両方で確認。
  2. 過去日のダイジェストを再構築できるか（Med）→ 通知内容は、その日の保存済み snapshot（暗号化。scan ジョブは鍵を持つ）から作る必要がある。snapshot の復号・candidate の読み込み・本文の再構築が、既存の関数（`build_digest` など）で可能かを確認する。
  3. 何日前まで回収するか、古い通知を今送る価値があるか（要判断）→ 設計判断を含む。
- **修正方針の候補（未確定）:** (a) 通常実行で、直近 N 営業日の pending を、保存済み snapshot から再構築して再送する（N は小さく。例: 3）。(b) 回収はせず、`playbooks.md` を「再試行は同じ市場日の再実行と手動再送のみ」と修正する。(a) を採る場合は、重複を抑える（`succeeded` を書く）ことと、snapshot が無い・復号できない日の扱いを決める。
- **受入条件:** (a) なら、前日の pending が次の通常実行で送られて `succeeded` になり、二重には送られない。(b) なら、文書が実態と一致する。どちらでも exactly-once は保証しない前提を維持。既存の通知テストが無変更で PASS。
- **baseline への影響:** なし。**注意:** 方針（a か b、N の値）はユーザー判断が要る。`verify-before-fix` の途中で、選択肢を示して確認すること。

## ISSUE-21: `sent:state-save-failed` に警告アノテーションが出ない

- **出典 / 分類 / 重大度:** Claude 再調査（観察）/ A / 低
- **現象:** Slack が受理した後に状態の保存が失敗する（翌日に重複し得る）ケースは、status が `sent:state-save-failed` で、`failed:` で始まらないため、Actions の警告アノテーションが出ない。ログの status には出る。
